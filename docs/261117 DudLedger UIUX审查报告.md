# DudLedger UI/UX 全面审查报告

**审查日期**：2026-11-17  
**审查基准**：当前本地工作区源码  
**第一轮范围**：产品设计审查、关键线框方案、设计规范与实施优先级；不修改产品代码

## 一、结论先行

DudLedger 已经具备一套相当完整的本地尽调查账闭环：导入预检、分录重组凭证、跨页选择、关注与备注、问题归集、快照留存、AI 发送前确认，都不是表面功能。当前最需要解决的不是“界面不够圆”或“颜色不够高级”，而是：

> **业务骨架已经专业，但工作区布局、操作范围反馈和组件语言尚未达到同一成熟度。**

建议不做换肤式重构，也不引入复杂 Dashboard。正确方向是：

1. **先保护查账主链路**：账表可读性、搜索筛选、连续核查、选择与归集反馈。
2. **再统一产品语言**：减少重复边框和相互竞争的按钮，收敛字体、数字、控件状态及弹窗规范。
3. **保留现有品牌基调**：暖灰、米白、低饱和陶土色继续做，但更克制、更安静。
4. **保持桌面工具密度**：不靠大留白、大标题、卡片堆叠或装饰动效制造“设计感”。

最终感应接近 Claude Code 式的简约：信息清楚、界面退后、操作直接，同时保留财务软件所需的表格密度和数字可比较性。

## 三、当前产品做得好的地方

这些部分应保留，不应在视觉升级中被误删或弱化：

1. **本地查账闭环完整**：从导入、科目、明细到凭证、关注和问题归集，主任务不是依赖 AI 才能成立。
2. **财务数据保护意识较强**：文件指纹、预检、重复导入处理、按工作表提交、快照与变化复核均有实现。
3. **批量操作有专业基础**：同凭证分录自动去重、跨页勾选、Shift 连续选择、框选复制和合计，适合真实查账。
4. **记录安全性较成熟**：备注自动保存、冲突保护、失败保留输入，比许多简单内部工具完整。
5. **AI 凭证抽查有明确边界**：发送前展示实际字段并等待确认，取消默认可用，应作为其他 AI 流程的参照。
6. **视觉基调已有辨识度**：`theme.py` 的暖色中性色和陶土主色并不廉价，问题主要是执行不一致，而非方向错误。

## 四、总体诊断

### 4.1 视觉审美

当前界面已有“安静”的基础，但仍有三类不统一：

- **控件语言不统一**：ttk 直角按钮与 Canvas 圆角按钮并行；主操作在不同窗口中的样式和位置不稳定。
- **层级依赖边框而非排版**：表头、工具条、面板、输入框和底部区域都有边界，界面容易显得由许多矩形拼成。
- **颜色语义没有彻底收口**：全局 token 之外仍有借贷行色、关注行色和提示色硬编码，部分颜色同时承担装饰与状态含义。

因此，解决方式不是把所有控件改成更大的圆角，而是减少无意义边界、建立稳定对齐和明确的文字/数字层级。

### 4.2 布局与密度

默认 1160×690 对单账表基本可用，但打开右侧问题工作台后，布局从“账表为主”变成“账表与编辑器争宽”。当前策略是压缩所有列，空间继续不足时自动拆出独立窗口。这两个动作都可能破坏上下文：

- 列被压缩后，摘要、科目和往来单位需要悬停才能读全。
- 自动出现新窗口会改变用户正在理解的界面空间。

专业工具应优先保持主表关键列可读，让辅助面板适应主任务，而不是反过来。

### 4.3 交互与反馈

当前最影响效率的不是点击次数本身，而是**用户需要记住界面没有说清楚的规则**：

- 勾选凭证优先于框选范围，但视觉上像两套同级选择。
- 加入问题会自动关注，但确认前没有明确说明。
- 当前源码缺少可见的全字段明细搜索入口。
- 凭证窗口没有上一张/下一张，连续过凭证需要反复回列表。
- 部分空状态无法区分“真的没有数据”和“筛选后没有结果”。

### 4.4 产品完成度

从商业级桌面软件标准看，当前像“功能已成型、设计系统尚未收口”的产品，而不是需要推倒重来的开发原型。主要缺口是：

- 高频工作流尚未围绕真实核查节奏组织。
- 组件状态、键盘焦点和字号缩放覆盖不完整。
- 入口归属与页面上下文不够一致，例如所有页面始终显示主色“导入表格”。
- 历史截图、旧文档与当前界面存在差异，需要避免它们继续影响产品沟通。

## 五、最值得重新设计的八个区域

### 区域 1：明细账与问题工作台的空间关系

**优先级：P0；难度：中高**

### 当前问题

- 代码确认：右侧问题区默认宽 400px，计算器 300px；空间不足会自动把问题区拆成独立窗口（`workbench.py:167-218, 584-620`）。
- 代码确认：工具区打开时，表格按可用空间压缩列宽，而不是优先保护摘要、往来单位和金额的可读性（`table_layout.py:22-71`）。
- 历史截图可见：工作台打开后，主表多列被截断并出现横向滚动，右侧编辑区却有较大空白。

### 为什么是设计问题

“看账—判断—归集—记录”是一个连续任务。当前布局把辅助记录区与原始账表放在同一优先级，导致辅助功能打开后，主任务反而变难。

### 建议改成什么样

1. 主表设置**可读宽度下限**，不再对所有列等比例挤压；超出时保留横向滚动。
2. 问题区推荐宽度改为 360px，可在 320–420px 间调整；实际阈值由真实窗口测试校准。
3. 窗口足够宽时停靠右侧；不足时改为**覆盖式抽屉**或保持收起，由用户主动打开，不再自动拆窗。
4. “独立窗口”保留为用户显式选择，不作为系统自动响应。
5. 问题详情顶部增加持续可见的“当前问题”切换入口，减少返回目录才能换问题的次数。
6. 相关凭证保持默认主视图；问题描述和笔记按需要展开，不让空编辑器长期占据高度。

### 修改后的交互

用户打开问题区后，仍能直接读摘要和金额；缩窄窗口不会突然出现新窗口；切换问题不必反复返回目录。

### 效率改善

减少悬停读全文、横向寻找金额、窗口重新定位和目录往返，提升连续归集效率。

### 区域 2：明细搜索、筛选与排序

**优先级：P0；难度：中**

### 当前问题

- 代码确认：当前明细工具条没有通用搜索输入框；可见关键词筛选主要是“摘要包含”（`ui.py:2185-2257`，`detail_filter_ui.py:135-141`）。
- 代码确认：后端已有更广义搜索能力，但当前主界面没有对应入口。
- 代码确认：日期、摘要、借贷和原币筛选入口依附于列表头，排序也主要藏在筛选弹窗中。
- 历史截图可见：旧版曾有长搜索框，说明当前源码与历史界面存在差异。

### 为什么是设计问题

律师查账经常从凭证号、往来单位、辅助核算或模糊关键词开始，而不总是从科目和摘要开始。入口缺失会直接改变产品真实可用性，不只是视觉问题。

### 建议改成什么样

采用一条稳定的主查询条：

```text
[科目范围：全部科目 ⌄] [搜索摘要、凭证号、科目、往来单位、辅助核算…] [筛选 2] [更多]
```

- 搜索框默认获得明确占位说明，Enter 执行，`Cmd/Ctrl+F` 聚焦。
- 筛选按钮显示激活数量；已启用条件在下一行以可删除 chips 呈现，没有条件时不占高度。
- 科目范围与列筛选都属于查询条件，但分别显示，清除动作明确区分“清除搜索/筛选”和“清除科目范围”。
- 保留列筛选弹窗的完整能力；排序状态应在表头直接可见，不只在弹窗内可见。
- 查询执行期间保持旧结果和结构稳定，避免控件跳动。

### 修改后的交互

用户无需先理解五类列筛选，即可从最熟悉的线索开始；进入复杂筛选时仍有完整控制。

### 效率改善

减少查找往来单位、凭证号和辅助核算时的绕行，也降低“到底有哪些条件正在生效”的认知成本。

### 区域 3：凭证选择、详情与连续核查

**优先级：P0；难度：中高**

### 当前问题

- 代码确认：勾选凭证与单元格框选并存；只要存在勾选，后续操作就使用勾选范围（`voucher_selection.py:34-39`）。
- 代码确认：当前有跨页张数提示，但操作按钮本身只显示数量，不突出“来自勾选还是框选”。
- 代码确认：明细主要靠双击打开凭证，没有 Enter 打开；凭证窗口没有上一张/下一张。
- 代码确认：默认新凭证会替换旧窗口；来源行虽存入数据，普通凭证默认可选列却排除了来源。
- 历史截图可见：凭证窗口存在较大空白，操作、合计和备注入口分散；当前版本已有紧凑高度逻辑，实际表现仍待实测。

### 为什么是设计问题

连续核查是核心工作，不应要求用户反复“回列表—找下一行—双击”。选择优先级若不够透明，则可能对新框选凭证执行了旧勾选范围的操作。

### 建议改成什么样

1. 选择反馈改为明确的上下文条：
   - `已勾选 3 张凭证（含跨页 1 张）· 后续操作使用勾选范围`
   - `当前框选涉及 2 张凭证 · 尚未勾选`
2. 勾选与框选使用不同视觉语义；存在旧勾选时，执行按钮旁显示范围来源。
3. 支持 Enter 打开当前凭证；凭证窗口增加“上一张 / 下一张”和“第 n / N 张”，顺序继承当前筛选结果。
4. 凭证头部直接显示日期、凭证字/号、来源和复核状态，不再只写“已导入的凭证分录”。
5. 表格按实际分录数控制高度，常见两至六行凭证不出现大块空白。
6. 底部固定显示借贷合计与差额；差额异常使用语义色，正常状态不抢眼。
7. 备注继续默认折叠，但关注状态直接可见；来源行提供一键复制或查看，不要求用户寻找隐藏列。

### 修改后的交互

用户可以留在同一个核查窗口内连续过凭证，只在需要备注或归集时展开辅助操作；每次批量操作前都知道实际作用范围。

### 效率改善

减少列表往返和重复双击，降低跨页勾选导致误操作的风险，增强审计追溯。

对应线框图见第九部分图 3。

### 区域 4：关注、问题归集与复核状态

**优先级：P0（状态透明）＋P1（效率）；难度：中**

### 当前问题

- 代码确认：加入问题会自动写入关注记录（`issue_store.py:89-103`），但选择器只提示“加入问题、跳过已有关联”（`workbench.py:851-886`）。
- 代码确认：问题选择器无搜索、无 Enter 确认、无最近使用；问题多时需要长列表寻找。
- 代码确认：新建并加入后仍留在目录，若紧接着写问题记录还需再次进入详情。
- 代码确认：问题快照复核与关注页复核是两套状态，目前通过文案分开说明，但入口分散。

### 为什么是设计问题

隐性副作用会破坏用户对账套状态的理解；复核状态相近但不同步，也增加“我到底确认了什么”的负担。

### 建议改成什么样

1. 归集确认区直接写：`将加入所选问题，并同步加入关注；已有备注不会覆盖。`
2. 问题选择器增加搜索、最近使用和当前问题置顶；Enter 加入所选，双击行为保留。
3. 若当前已有打开的问题，提供低门槛主操作：`加入当前问题`，其他问题通过下拉选择。
4. 新建并加入后提供两个明确后续动作：`查看问题` 或 `继续核查`，不强制跳转。
5. 完成反馈不仅写“新增/已存在”，还写明目标问题及是否同步关注。
6. 复核按钮按场景区分：`确认问题快照已复核` 与 `确认关注记录已复核`，避免只写“确认复核”。

### 修改后的交互

归集动作可预测，键盘流程完整；用户不需要事后发现关注列表变化，也不会混淆两类复核。

### 效率改善

问题数量增长后仍能快速归集，减少重复选择和状态核对。

### 区域 5：左侧导航、顶栏与功能归属

**优先级：P1；难度：中**

### 当前问题

- 代码确认：默认 56px 纯图标导航，450ms 后才有悬停名称（`navigation.py:67-96`）。
- 代码确认：页面、问题工具、计算器、主体名单、设置和账套共享同一栏，领域功能靠抽象图标识别。
- 代码确认：顶栏“导入表格”在所有页面保持陶土主色，包括关注和 AI 页面。
- 代码确认：导入记录、核对提醒等入口还分布在账套或系统菜单中。

### 为什么是设计问题

图标栏节省空间，但“AI 尽调线索”“尽调主体名单”不是通用图标能自然表达的概念。全局导入按钮持续占据最强视觉层级，让辅助页面也围绕导入组织。

### 建议改成什么样

1. 保留可收起侧栏，但宽屏/首次使用默认显示“图标＋文字”，用户主动收起后记住选择。
2. 导航分为两组：`账簿浏览`（科目、明细、报表）与`核查处理`（关注、问题、AI）。
3. 计算器、主体名单作为工具入口，视觉上弱于主页面；设置与账套继续固定底部。
4. 选中项使用细色条或浅底＋文字，不只依赖图标颜色；Hover 提示缩短到约 250–300ms，并支持键盘焦点。
5. 顶栏主操作随页面变化：欢迎/账簿页可突出导入，关注页突出导出或归集，AI 页突出开始抽查；其他时候导入退为普通按钮或账套菜单项。
6. 页面标题保持 15–16px，不做展示型大标题。

### 修改后的交互

用户可以从文字理解功能，从当前页面理解下一步；侧栏仍可为熟练用户压缩，但不以学习成本换空间。

### 效率改善

降低首次和间歇使用的识别成本，减少跨菜单寻找工具。

### 区域 6：导入、字段映射与预检

**优先级：P1；难度：中高**

### 当前问题

- 代码确认：单表导入同时放置工作表、表类型、表头行、AI、Agent、文本预览、最多十余项映射和底部提示（`ui.py:1106-1149, 1233-1264`）。
- 代码确认：批量导入标题即“自动审查”，小文件窗口建立后自动开始；无 Key 时可能先出现 AI 错误，本地模式位于“手动设置”二级菜单（`ui.py:1429-1516, 1593-1611`）。
- 代码确认：批量页同时包含进度、工作表列表、当前表详情、手动设置、AI 设置和 Agent 操作。
- 历史截图限制：现有 `03_import.png` 内容不完整，本轮不据此判断最新导入窗口的实际比例。

### 为什么是设计问题

导入本应是“把本地账簿放进来”的低门槛动作，当前却让 AI 审查成为首要心智。信息同时出现也削弱了错误定位与下一步判断。

### 建议改成什么样

保留现有窗口和功能，重组为三个清楚阶段：

1. **选择工作表**：目标账套、文件与工作表清单、导入范围。
2. **确认字段与预检**：左侧工作表列表，右侧预览与映射；问题直接定位到工作表/字段。
3. **完成导入**：成功、跳过、失败及后续查看入口。

具体交互：

- 默认先走本地规则；页面提供明确的 `AI 辅助识别（可选）`，未配置 Key 时直接引导设置或继续本地，不制造整列错误。
- 启用 AI 前用一行说明发送范围；涉及真实账目时增加轻量确认，不沿用“默认自动发送”的心智。
- 字段映射分为必需字段、常用字段和可选字段；可选字段折叠但不删除。
- 原表预览与映射保持同屏，避免在文本说明、映射和底部日志之间来回滚动。
- Agent 接手收入“需要协助”菜单，不与确认导入争夺层级。
- 底部只保留当前阶段最重要的状态与主按钮。

### 修改后的交互

用户先理解导入范围，再解决具体字段问题；AI 是可调用的工具，而不是前置门槛。

### 效率改善

减少批量工作表中的错误定位时间，降低首次导入和隐私判断负担。

### 区域 7：AI 尽调线索与辅助工具

**优先级：P1；难度：中**

### 当前问题

- 代码确认：AI 页面同时出现开始/停止、专项科目、多选范围、提示词设置、进度、动态分类、历史批次、六种结果通道和科目/期间筛选（`jev_ui.py:193-266, 283-315`）。
- 代码确认：未选专项科目时实际表示审查全部已设置科目，这一语义需要用户阅读说明才能理解。
- 代码确认：AI 不继承当前明细筛选，从明细进入 AI 时范围关系不够直观。
- 代码确认：AI 详情复用了凭证数据，但普通凭证已有的部分本地复核能力并未完整复用。
- 历史截图可见：空结果页仍有大面积表格和控制项，主任务入口与结果阅读没有明显阶段差异。

### 为什么是设计问题

问题不在功能多，而在所有功能同时平等出现。AI 应帮助用户处理线索，而不是让用户先管理一套批次、通道和规则系统。

### 建议改成什么样

1. 首屏只保留：`待核线索数量 / 当前批次 / 开始抽查 / 结果表`。
2. 主结果视图收敛为 `待核`、`已处理`、`全部`；失败、过期、不确定、已忽略等放入高级筛选，不删除任何状态。
3. 动态分类改为带数量的下拉或可换行 chips，避免固定七列网格在窄窗口挤压。
4. 专项科目默认收起为范围摘要，如`本次范围：6 个专项科目`；点击开始后再确认范围。
5. 从明细进入 AI 时明确选择：`使用当前筛选范围`或`按专项科目新建范围`；若技术上暂不继承，也必须直接说明。
6. 历史批次和规则配置各保留一个稳定入口，避免重复设置按钮。
7. AI 详情沿用统一凭证核查窗口，将模型判断、核查建议、忽略线索作为辅助区；原始凭证和本地复制/计算能力保持完整。
8. 保留现有发送前逐页预览与确认，这是当前 AI 交互中最成熟的部分。

### 修改后的交互

用户主要处理“哪些线索待核、下一条是什么”，需要时才管理分类、历史和规则。

### 效率改善

减少结果页认知负荷，让 AI 线索更自然地回到本地凭证核查。

### 区域 8：组件、表格、反馈与空状态

**优先级：P1；难度：中**

### 当前问题

- 代码确认：ttk 按钮和 Canvas 圆角按钮并行；不同窗口主操作样式不一致（`theme.py:90-128`，`widgets.py:29-161`）。
- 代码确认：圆角 Canvas 按钮虽支持键盘触发，但没有清楚的绘制焦点态。
- 代码确认：金额右对齐，但未统一使用等宽数字；字号放大并未覆盖所有派生字体与工具。
- 代码确认：关注搜索无结果与真正无关注共用空状态；科目范围不计入明细筛选空状态计数（`ui.py:3194-3233`）。
- 历史截图可见：部分弱提示文字对比偏低，表格外横向滚动与多行底部提示占用空间。

### 为什么是设计问题

成熟的质感来自同一个控件在任何页面都有相同表现，也来自用户总能理解当前状态和恢复动作。局部圆角不能弥补这些不一致。

### 建议改成什么样

1. 统一按钮层级：每页最多一个主按钮；次按钮、静默按钮、危险按钮各有固定样式和位置。
2. 统一输入框高度、边框、焦点和错误状态；弹窗底部主按钮固定右侧，取消在其左。
3. 表格默认行高维持约 30–32px，可提供 26–28px 紧凑模式；不减少当前默认可见行数。
4. 金额使用等宽数字字体，借方/贷方列宽至少容纳常见大额、千分位和两位小数。
5. 表格选中、关注、异常和借贷方向不再混用同一类浅色背景；每行最多保留一个主状态背景。
6. 空状态分为：无账套、无业务数据、搜索无结果、筛选无结果、当前科目无分录、数据过期/未匹配。
7. 所有搜索无结果状态提供`清除搜索`或`清除筛选`，不误导用户重新导入。
8. 反馈按打扰程度分层：行内/状态栏用于成功，非模态提示用于可恢复问题，模态框只用于确认和必须处理的错误。

### 修改后的交互

控件行为更一致，数字更易比较，空状态能指导下一次动作，成功反馈不再频繁打断。

### 效率改善

降低视觉扫描和错误恢复成本，提升大字号与键盘操作的可用性。

## 六、推荐的整体视觉方向

### 6.1 设计概念：安静的账簿工作台

关键词：**克制、清晰、紧凑、可信、可回溯**。

不建议把 DudLedger 做成深色极客工具，也不建议做成卡片式 SaaS Dashboard。更合适的是：

- 暖白工作区像纸张，表格是真正的主体。
- 陶土色只标识当前最重要的动作或激活状态。
- 分隔线很细，面板主要靠对齐和背景差分层。
- 圆角存在但不显眼，不成为设计语言的主角。
- AI 不使用大面积紫色、渐变或发光效果，与普通核查工具共享语言。

### 6.2 需要减少的元素

- 同一视图内重复的外框与 LabelFrame。
- 所有页面常驻的主色导入按钮。
- 大面积无数据白表与无意义空白编辑区。
- 过多并列筛选项、长说明文字和常驻操作提示。
- 为圆角而新增 Canvas 容器或自绘复杂控件。

### 6.3 需要加强的元素

- 当前科目、当前筛选、当前凭证和当前问题的上下文。
- 数字列、凭证号和日期的扫描效率。
- 选择范围、保存状态和复核状态的可见性。
- 键盘焦点、按钮主次和弹窗操作的一致性。

## 七、DudLedger 设计规范 1.0 建议

### 7.1 色彩与语义色

以现有 token 为基础，不追求大幅换色：

| 角色 | 建议值 | 用途 |
|---|---|---|
| Canvas | `#FAF9F5` | 主窗口背景 |
| Sidebar | `#F0EEE6` | 导航与低层级区域 |
| Surface | `#FFFFFF` | 表格、输入与必要阅读表面 |
| Sunken | `#F5F3EC` | 表头、轻量工具区 |
| Ink | `#30302C` | 主文字 |
| Ink Soft | `#53524C` | 次文字 |
| Muted | `#77766F` | 辅助说明；需验证小字对比度 |
| Border | `#E3E0D7` | 默认细分隔线 |
| Border Strong | `#D4D0C6` | 输入框和必要控件边界 |
| Accent | `#A65036` | 唯一主操作、激活标记 |
| Accent Soft | `#F1E3DD` | 选中或轻量强调背景 |
| Success | `#356348` | 已完成、平衡等正向状态 |
| Warning | `#8A6D1A` | 待复核、口径提醒 |
| Danger | `#9E3B2E` | 删除、失败、真正异常 |

规则：

- 陶土色不大面积铺底，不同时突出多个按钮。
- 状态不能只靠颜色表达，需配文字或图标。
- 正文对比度目标至少 4.5:1，大字和关键控件边界至少 3:1；最终实现需实测，而不是只凭色值判断。
- 借贷方向优先用列位置和标题表达，不建议长期用整行蓝/棕色区分。

### 7.2 字体、字号与数字

| 层级 | 建议 |
|---|---|
| 页面标题 | 15–16px，Semibold |
| 区块标题 | 12–13px，Semibold |
| 正文/表格 | 12–13px，Regular |
| 辅助说明 | 11–12px，Regular，不用于关键操作 |
| 表格金额 | 与表格同号，Menlo/系统等宽数字，右对齐 |
| 凭证合计 | 13–14px，Semibold，等宽数字 |

- macOS 中文优先系统字体/PingFang SC，Windows 使用系统 UI 字体；不为跨平台像素一致而嵌入庞大字体。
- 金额、数量、页码尽量使用等宽数字，保证上下行比较。
- 全局字号调整必须同步表格行高、按钮、标题、备注、计算器和弹窗，不只放大部分文字。

### 7.3 圆角、边框与阴影

- 普通控件推荐 4px，菜单/小弹层可用 6px；大型面板不必强行圆角。
- 表格、侧栏和主工作区以直角和细分隔线为主，避免“卡片套卡片”。
- 默认边框 1px、低对比；焦点边框与普通边框明确区分。
- 阴影只用于真正浮于内容之上的菜单、弹窗或抽屉，且保持很浅；停靠面板不用阴影。
- Tkinter 不应为所有面板自绘圆角和阴影。优先共享 ttk 样式和布局，Canvas 仅用于确有价值的少量控件。

### 7.4 间距与尺寸

采用 4px 基线：

| Token | 值 | 常见用途 |
|---|---:|---|
| Space 1 | 4px | 图标与文字、紧凑控件间隔 |
| Space 2 | 8px | 同组控件、表头内边距 |
| Space 3 | 12px | 工具条、表单组间距 |
| Space 4 | 16px | 页面左右边距、主要分组 |
| Space 6 | 24px | 弹窗大分区，不用于每行表格 |

- 主内容页左右 16px，上下 8–12px；不再叠加无意义容器 padding。
- 表格行高默认 30–32px，紧凑 26–28px；两种模式都保留完整数字和焦点可见性。
- 图标按钮命中区域建议至少 28×28px，即使图标本身只有 16–20px。

### 7.5 图标

- 统一 16/20px 线性图标，笔画和视觉重量一致。
- 导航抽象功能保留文字；纯图标模式提供快速 tooltip 与键盘焦点名称。
- 关注、待复核、已保存等状态使用固定形状，不以emoji代替产品图标。
- 选中图标可配合浅底或左侧 2px 指示条，避免仅换颜色。

### 7.6 按钮、输入框、菜单与弹窗

**按钮**

- Primary：每个视图最多一个；仅用于当前阶段主动作。
- Secondary：常规执行动作，白底细边框。
- Ghost：导航、展开、工具切换和低层级操作。
- Danger：只用于删除/移除等需确认动作。

**输入框**

- 标签与输入关系稳定；错误显示在对应字段附近，不只写到底部。
- 搜索框有明确范围占位符和清除动作。
- Disabled 仍需可读，不仅把文字调至极浅。

**菜单**

- 高频动作不放“更多”；更多只承载显示列、导出、恢复默认等次级操作。
- 原生菜单可保留系统外观，不必为视觉统一自绘；必须统一分组、命名、快捷键和危险项位置。

**弹窗**

- 标题说明任务，正文只保留当前任务，底部右侧主按钮、其左取消。
- 凭证查看是非模态连续工具；导入和设置按任务需要模态化。
- 不用自动拆窗解决响应式；窗口尺寸应随屏幕和内容收敛。

### 7.7 表格与状态

- 表头固定，激活筛选和排序有清晰但克制的标记。
- 行 Hover 只提供轻微底色，不与选中/关注混淆。
- 选中行、勾选凭证、框选单元格是三种不同状态，文案和视觉不得混用。
- 金额空值与 0 保持现有区别，并通过对齐和占位符增强可读性。
- 长文本优先给摘要足够弹性； tooltip 是补充，不应成为正常阅读的必经步骤。

### 7.8 控件状态矩阵

所有共享控件至少覆盖：

| 状态 | 设计原则 |
|---|---|
| Default | 层级稳定，不靠高饱和吸引注意 |
| Hover | 轻背景或边框变化，无布局位移 |
| Pressed | 轻微加深，立即反馈 |
| Selected | 浅底＋文字/指示条，持久可见 |
| Focus | 清晰可见的 1–2px 焦点环，与 Hover 不同 |
| Disabled | 不可操作且仍可读，必要时解释原因 |
| Loading | 保留原布局，防止按钮与表格跳动 |
| Danger | 仅用于破坏性动作或真实错误 |

### 7.9 动效

- 桌面 Tk 界面默认以即时、稳定为先，不为按钮和表格逐行加动效。
- 抽屉、展开收起可使用约 120–160ms、ease-out 的短过渡；若实现成本高或影响响应，宁可不做。
- 进度条只表达真实进度；无法确定时明确写“正在处理”，不伪装百分比。
- 数字、金额、选中状态不做滚动或闪烁动画。

## 十、推荐实施顺序

### 阶段 1：先修核心工作区，不动业务数据

- 主表宽度保护、工作台停靠/覆盖/独立窗口策略。
- 明细搜索入口、筛选条件呈现。
- 选择范围文案与自动关注提示。

重点文件：`ui.py`、`workbench.py`、`table_layout.py`、`voucher_selection.py`。

### 阶段 2：连续核查与归集效率

- 凭证 Enter、前后导航、来源追溯、窗口内容适配。
- 问题选择搜索、最近使用、键盘确认、归集后反馈。

重点文件：`ui.py`、`workbench.py`、`voucher_actions` 相关实现；保持 `issue_store.py` 数据逻辑不变，除非用户另行决定业务规则。

### 阶段 3：导航、导入与 AI 信息架构

- 导航分组与上下文顶栏。
- 导入阶段重组、本地优先、AI 明确可选。
- AI 结果主从收纳与统一凭证详情。

重点文件：`ui.py`、`navigation.py`、`jev_ui.py`。

### 阶段 4：设计系统收口

- 颜色、字体、间距、按钮和弹窗规范。
- 表格数字、焦点、空状态和快捷键发现。
- 最后才评估必要动效，不以动画掩盖布局问题。

重点文件：`theme.py`、`widgets.py`、`table_tools.py`、`empty_state.py` 及各页面调用点。

## 十一、后续实测验收矩阵

后续若批准实施，不运行全套无关测试，只覆盖修改及关联功能；真实视觉验收需在隔离显示环境进行。

| 场景 | 必须确认 |
|---|---|
| 1160×690 默认窗口 | 主表关键列可读，主按钮唯一，纵向空间不被提示侵占 |
| 820×520 最小窗口 | 不自动弹出工作台，主要操作仍可到达 |
| 侧栏＋科目树＋工作台同时打开 | 有明确降级策略，不出现全列严重截断 |
| 大字号 | 标题、表格、备注、计算器与弹窗同步缩放 |
| 勾选后又框选 | 用户能看到实际操作范围，可一键清除旧勾选 |
| 跨页勾选 | 张数、来源范围和清除行为一致 |
| 连续打开凭证 | Enter、上一张/下一张、Esc 返回及备注保存不冲突 |
| 加入问题 | 自动关注、已有备注、目标问题和结果数量均透明 |
| 搜索/筛选无结果 | 显示正确原因和恢复动作，不建议重新导入 |
| AI 空/运行/失败/过期 | 页面主次稳定，结果处理不依赖理解全部通道 |
| 借贷与多币种选区计算 | 合计口径有明确提示，不误导为自动净额 |
| 键盘操作 | Focus 可见，Enter/Esc 不冲突，文本编辑时不误触全局快捷键 |

## 十二、最终建议

第一轮实施不应从“全局替换圆角和颜色”开始，而应先完成三个最能被真实使用感知的改变：

1. **打开问题工作台时，账表仍然好读。**
2. **从任意线索开始搜索，并始终知道选中了哪些凭证。**
3. **连续打开、核查和归集凭证，不必反复回列表。**

这三项完成后，再通过克制的色彩、字体、边框与状态规范统一外观。这样得到的是一次工作方式升级，而不是一次 CSS 式美化；也更符合 DudLedger 作为专业财务审查工作台的定位。
