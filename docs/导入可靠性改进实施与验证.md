# Excel 导入可靠性改进：实施与验证

对应计划：《DudLedger Excel 导入可靠性改进计划》（2026-09-27，与 GPT Astra 讨论定稿）。
本文是该轮实施的中文研究记录与测试对照报告。本轮已完成代码修改并全部通过本地测试。

## 一、目标回顾

同时解决“导入失败”与“导入成功但数据有误”，操作方式为**自动处理、集中确认疑点**。
整体流程按计划落地为：

**读取原表 → 识别区域和表头 → 模板/规则匹配 → 必要时模型辅助 → 整表试解析 → 确认疑点 → 正式导入**

## 二、成熟做法的落地方式

| 借鉴来源 | 计划要点 | 本轮落地 |
|---|---|---|
| Power Query | 先定位数据区域，再识别表头和字段 | 表头扫描窗口解除“前 20 行”限制（前 30 行内全扫；使用者导入前会手动整理表格，更深的表头填行号即可），候选按映射命中数择优 |
| Power Query 数据分析 | 抽样识别与整表校验分开 | 模型只看预览（建议列）；`precheck.py` 对整表逐行分类校验，两者分离 |
| OpenRefine | 导入前预览、疑点可局部修正 | PrecheckDialog 展示“原单元格 → 当前解释 → 问题原因 → 可选处理”，可排除所选行并立即重新预检 |
| react-spreadsheet-import | “列匹配正确”与“数据可导入”两步检查 | 列映射经 `ImportSpec.validate`（第一步）；整表预检确认每行可解析（第二步），关键错误阻塞该表 |

## 三、分层实施明细

### 1. `ledger_viewer/importer.py`（结构识别与行级分类）

- **行级分类器 `classify_rows`**：单一裁判，逐行产出 `RowDecision`（去向 + 原因 + 数据 + 行级警告）。去向分为导入、待处理（关键错误）、以及带原因的排除（表头/标题/空行/小计/页脚/维度子行/无金额行/人工排除/数据区域外）。`normalized_rows` 变为它的严格包装（待处理即抛错），保持旧调用与事务回滚语义。
- **合并单元格表头**：新增 `merged_ranges`（xlsx 完整加载一次取合并区域，xls 用 xlrd，按文件缓存）；`combine_header` 按列拼接两层表头，“借方/贷方”子标题继承左侧最近组名，同时覆盖“真实合并”与“纯留白”两种画法，区分期初/本期/本年累计/期末的借贷列。报表类型保持原能力。
- **表头扫描**：`guess_header` 在前 30 行窗口内扫描（原 20 行；使用者导入前会手动整理表格，标题区不深，更深的表头填行号即可），行数据缓存避免重复读文件。
- **重复表头与分区**：与首表头结构一致的重复表头行自动识别为分区边界并跳过（连续分区合并）；命中 ≥3 个已知表头别名但结构不同的行判为“疑似另一张表”，该行及其下方所有行均标记待处理（不同结构的分区绝不按当前列静默导入）；原表头再次出现时恢复。
- **CSV**：`detect_csv` 依次尝试 utf-8-sig / utf-16(BOM) / gb18030，尾部截断的多字节字符容错重试；分隔符由 `csv.Sniffer` 在 `,;\t|` 中判定，失败回退逗号。结果按（路径、mtime、大小）缓存。
- **公式缓存缺失**：`formula_cells` 以 `data_only=False` 扫描公式坐标；分类时映射列的值为空且该格是公式 → 待处理（openpyxl 不计算公式，绝不把缺缓存当零）。
- **期间冲突**：期间列/年度列与日期推算不一致 → 待处理（原来是静默取列值）。
- **日期无法识别**：按原文保留并给行级警告（不猜测、不填零）。
- **有金额但无科目**（且上方无科目可继承）→ 待处理（原来静默跳行）。
- **页脚**：`第N页/共N页/打印时间/制表人` 等模式识别为页脚排除。
- **`ImportSpec` 扩展**（旧调用兼容）：`data_start_row`、`data_end_row`（数据区域）、`excluded_rows`（人工排除行）；`with_extra_exclusions` 供疑点界面使用；`validate` 增加对应校验。

### 2. `ledger_viewer/precheck.py`（整表预检，新模块）

- `precheck(spec)` 产出 `PrecheckResult`：文件指纹（SHA-256）、`PrecheckStats`（拟导入行数、借贷合计、来源行范围、逐类排除计数）、疑点列表、待处理行号、排除行样本。
- 疑点分级：**关键**（金额/方向无法识别、期间冲突、公式缓存缺失、结构变化、无科目金额行、无可导入行）阻塞该表；**提醒**（日期无法识别、续行缺凭证、未映射疑似金额列、原表合计不一致）不阻塞；**说明**（与原表合计一致）。
- 解析问题与原账簿自身差异分开：原表合计与拟导入合计的对照仅在口径明确（借贷两列均映射且存在小计行金额）时进行，不一致只提示待核，不阻止导入、不修改账目。
- 未映射列画像：非空单元格大多可识别为非零金额且达数量门槛 → 提示“疑似金额列未映射”。
- `build_import_report` 生成中文 Markdown 质量报告。
- 预检只读不改账套；`blocked = 存在待处理行 或 无可导入行`。

### 3. `ledger_viewer/store.py`（账套 v7 增量迁移）

- 新表：`import_templates`（kind + 表头结构签名唯一，used_count / last_used_at）、`import_prechecks`（来源关联、结论、统计 JSON、疑点 JSON，随来源级联删除）。旧账套升级到 v7，原有数据不动。
- `import_sheet` 与预检共用 `classify_rows`：待处理行照旧抛错回滚；成功后同事务写入预检记录（含实际排除统计与行级警告）并按表头签名保存模板。
- 模板按**表头结构签名**匹配（与文件名无关），套用时仍过 `ImportSpec.validate` 与列宽校验；结构变化即失配，回到本地规则。旧导入无预检记录，界面标“无历史预检报告（旧版导入）”，不追认新校验。
- `export_import_report(path)` 导出质量报告。

### 4. 模型层（jev_mapping / deepseek_mapping）

- 预览列上限 20 → 40（宽表按列分块；行仍为前 20 行，超出部分交给本地规则）。
- **静默丢弃 → 显式警告**：Jev 两字段争同一列时按置信度保留并提示落选字段；DeepSeek 对超范围/无法解析/占列冲突/多余字段逐条提示。两个模型继续共用 `critical_warnings` 与同一套本地校验；模型置信度只作内部排序，不展示为“导入准确率”。

### 5. `ledger_viewer/ui.py`（界面）

- 新增 `PrecheckDialog`：按“原单元格 → 当前解释 → 问题原因 → 可选处理”列示疑点与排除样本；支持多选行排除并自动重新预检；“继续导入”只放行无关键问题的表，被阻塞的表显示为暂停；单表模式可返回调整列设置。
- 单表导入（`ImportDialog.import_now`）：确认列后先预检；有疑点弹集中确认框，无疑点直接导入；预检后文件指纹变化会提示重新预检；完成提示含排除统计。
- 批量导入（`BatchImportDialog`）：预检所有选中表，有疑点的表集中确认；暂停表不写入、其余照常导入，结果汇总区分成功/暂停/跳过/失败及各表排除行数。
- 匹配顺序接入界面：批量与单表的自动识别均先查本地模板（`classify_sheet(templates=...)`），模板未命中再走本地规则；AI 建议仍为可选辅助。
- “导入记录”新增“导入预检”列（结论或“无历史预检报告”）；“文件 → 导出导入质量报告…”新增。
- 发送范围确认文案随预览列数动态更新（20 行 × 40 列 × 60 字）。

### 有意的行为变更（对应计划要求）

1. 期间/年度列与日期矛盾：静默取列值 → 阻塞并说明（待处理）。
2. 有金额但无科目且无可继承行：静默跳过 → 阻塞。
3. 公式结果缺失：当空值/零 → 阻塞并指明“文件未保存计算缓存”。
4. 模型重复占列/超范围字段：静默丢弃 → 列出提示（允许继续）。
5. 结构变化的分区：按当前列继续解析 → 该段全部待处理，明确提示拆分或排除。
6. 账套格式 v6 → v7（增量迁移，旧账套自动升级，数据不动）。

### 验收要求对照

- 已标注样本的关键金额、借贷方向、期间、来源行符合预期：合成样本全量断言 ✅。
- 无静默漏行/静默丢弃关键字段：行级去向 + 丢弃显式化 ✅；不支持的格式给出明确解释（现金流量表、无法确认的表仍要求人工设置列）✅。
- 失败导入/失败替换不破坏原账套：事务回滚测试保持通过 ✅。

## 五、边界与后续

- 首版范围与计划一致：明细账、序时账、科目余额表优先，资产负债表/利润表保持原能力；复杂交叉表、同表混排不同结构、任意格式重建不做自动转换，明确提示调整范围或使用模板。
- 表头扫描窗口为前 30 行（使用者导入前会手动整理表格，标题区不深；扫太深反而增加误判与开销）；超过该窗口的表头在导入对话框手动填行号。
- AI 预览仍为前 20 行 × 40 列；更深的表头依赖本地规则与模板。模型联网实测沿用发送范围确认，未在本轮自动执行。
- Excel 数值单元格的前导零在文件生成时已丢失，导入无法恢复；CSV 文本列的原样保留已由 raw_json 记录。
- 本地模板随账套保存；跨账套复用模板、疑点界面内直接编辑单元格值暂未提供（可排除行、返回调列或修正原表后重导）。

## 六、真实样本追加：单列金额＋借贷方向的序时账（2026-09-27）

使用者提供第一份真实失败样本：`江西比太序时账2020.1-2022.6 2.xls`（WPS 保存的用友打印导出，工作表名 `UFPrn…`，表头 `日期/凭证号数/科目编码/科目名称/摘要/币种/方向/数量/原币/金额`）。旧版无法识别的原因：序时账没有借贷分列，金额只有一列、借贷由“方向”列给出，而 entry 类型此前只认借方/贷方列；另“凭证号数”不在凭证号别名中。

### 改动

1. **entry 新增“金额（单列）”＋“借贷方向”两个字段**（`importer.py`）：自动识别、手工映射、Jev/DeepSeek 建议共用同一套字段清单；校验规则为单列金额必须同时映射方向列，方向只认 借/贷（含 Dr/Cr），识别不了的方向（含空值、金额非零的“平”）按疑点阻塞该行，不猜测。余额表的“余额＋方向”逻辑统一改用同一方向解析函数。
2. **别名补充**：凭证号增加“凭证号数”（凭证号“记-0001”这类字号合并形式原样保留，续行与凭证归并按整串工作）；金额增加“发生金额/发生额/本币金额”等；方向增加“借或贷”。
3. **成对合计行修复**：用友把总计打印成成对两行——“合计”只标在第一行，第二行除方向/金额外全空；旧逻辑会把第二行当续行导入并继承上一科目，导致贷方多出整整一笔总额。现紧邻合计行且无任何标识（科目/摘要/日期/凭证）的裸行按“合计行的续行”排除。
4. **预检降噪**：表头明示的数量/单价/汇率/税率等数值列不再按“疑似未映射金额列”提示；用友导出中的“数量”列因此不再误报。
4. **界面**：导入对话框 entry 字段列表加入“金额（单列）”与“借贷/余额方向”；提示文案加 wraplength，防止长文案在大字号下把“确认并导入”按钮挤出屏幕（该问题由既有大字号可见性测试捕获）。

### 验证

- 真实文件（只读冒烟）：自动识别为 entry（表头第 1 行，金额第 10 列、方向第 7 列、凭证号数第 2 列），预检“拟导入 3 行（借方合计 320,000.00 / 贷方合计 230,000.00）”，无阻塞疑点；导入后借贷落位与原表逐行一致，模板签名入库。
- 桌面真实语料复跑（`tests/manual_test_real_files.py`，9 文件 14 表）：两张原先“无法导入”的用友 UFPrn 序时账现可干净导入且借贷平衡——2020年1-12月序时账102.xls 7165 行（借=贷=342,788,343.91）、东莞捷固10月序时账.xls 239 行（借=贷=854,204.90），成对合计行各排除 2 行；语料整体 8/9 张表可干净导入（余下 1 张为航同资产负债表尾部签字区“财务负责人：”行触发既有的设计内疑点，人工排除即可）。
- 合成测试（`tests/test_precheck.py` 新增 7 项）：方向拆分与“平 0”排除、方向无法识别（含空方向）阻塞、缺方向列校验拒绝、成对合计行不导入、Dr/Cr 英文方向、余额表“方向＋期末余额”、数量列不误报。
- 回归：全量 150 项中除另一并行改动（DeepSeek 参数调整，非本轮内容）涉及的 3 项外全部通过；本轮相关模块 147 项全绿。

### 边界说明

- 单列金额模式下，原表“合计”行仍按摘要/科目名识别并排除，但预检不再做借贷合计对照（合计行只有一个混合方向的总额，口径不可比）。
- 明细账若出现“方向”指的是**余额**方向（借贷分列仍在）的版式，方向列照常映射但不参与分录方向，无影响；若整表只有“方向＋余额”而无借贷/发生额列，仍要求人工确认列，不会把滚动余额误当发生额导入。
